# Compatibility Pointer

The mandatory repository entrypoint is [AGENTS.md](./AGENTS.md). Use [docs/README.md](./docs/README.md) to open only the current contract needed for the task and [docs/repository-map.md](./docs/repository-map.md) for cross-repository ownership.

Do not add chronology here. Record notable app/tooling events in [changelog/app/](./changelog/app/), draft events in [changelog/drafts/](./changelog/drafts/), and reusable verified guidance under [ai-notes/](./ai-notes/). Use Git history only for targeted lookup of removed legacy memory, and verify historical claims against current code, workflows, manifests, and live state.

Local development must not provision or deploy AWS `dev` resources. Local drafts and harnesses remain first; any remote read needed from localhost uses the deployed `test` services and data.

The approved server-only integration foundation uses four independently deployable microservices: Data Spaces, Commerce, Integrations, and Notifications. Keep multiple small Lambdas within those service boundaries; do not create one repository per Lambda or add central platform-owner administration UI to Zoolandingpage. Drafts and public runtime must never contain provider credentials, payment or identity data, fiscal PII, bank data, raw provider payloads, server-only descriptors, repository metadata, or local work material. Frontend artifacts use an exact public JSON/media allowlist and must pass the generated-artifact boundary check before any AWS credential or upload step. Draft deployment validation runs without OIDC; only a dependent job for the exact validated commit may receive scoped OIDC. Every remote authoring operation requires an explicit environment; pulls additionally must match returned domain, resolved environment, and stage before cleaning or writing local files. Config Authoring deployment stays disabled until its repository-root SAM `CodeUri` is replaced by a verified allowlisted build artifact. Accountant answers, real Stripe volumes, written HostGator authorization or an approved alternative provider, and any open live-security incident remain production gates; do not infer tax defaults, activate Stripe Tax, enable real SMTP, capture live fiscal PII, provision production secrets, or authorize a dependent deployment until the gates in [the approved plan](./plan/infrastructure-server-only-integrations-1.md) are closed.

Draft deployment provenance must use the exact merged pull request associated with the target commit, not only Git ancestry. Require the same repository and the fixed `dev -> test -> main` source/base pair, the exact merge commit and second parent, the push event's exact first parent, and proof that the commit is still the target branch tip immediately before privileged deployment. Serialize deployments per repository/environment. GitHub Environments must allow only `test` for test and `main` for production, and each AWS OIDC trust policy must independently require that exact `ref` in addition to repository/environment. Provision roles only for drafts in `docs/drafts-registry.json`. The draft-repo bootstrap must report failure if native protection for either `test` or `main` or either exact Environment policy is absent; a workflow that blocks deployment is not a substitute for a protected branch or cloud-side trust restriction.

While protected draft branches require zero approvals, every identity with write and merge permission is a trusted deployment authority because repository code contains the workflow and verifier. If that trust set expands beyond fully trusted operators, require an independent reviewer or move privileged verification to an immutable reusable workflow outside the draft repository. Setup must pin the required `guard` check to the verified GitHub Actions app, allow no PR bypass identities, read branch and Environment protection back after writing it, anchor the GitHub owner to the registry, and reject ambiguous or invalid IAM role names before any AWS mutation.

All repository changes must be promoted by protected pull requests in order: `dev -> test -> main`. Before each promotion, synchronize the target branch history back into the source branch through a validated PR when needed so the promotion is conflict-free and no branch history is discarded.
