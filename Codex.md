# Compatibility Pointer

The mandatory repository entrypoint is [AGENTS.md](./AGENTS.md). Use [docs/README.md](./docs/README.md) to open only the current contract needed for the task and [docs/repository-map.md](./docs/repository-map.md) for cross-repository ownership.

Do not add chronology here. Record notable app/tooling events in [changelog/app/](./changelog/app/), draft events in [changelog/drafts/](./changelog/drafts/), and reusable verified guidance under [ai-notes/](./ai-notes/). Use Git history only for targeted lookup of removed legacy memory, and verify historical claims against current code, workflows, manifests, and live state.

Local development must not provision or deploy AWS `dev` resources. Local drafts and harnesses remain first; any remote read needed from localhost uses the deployed `test` services and data.

Server-only integrations use four independently deployable services: Data Spaces, Commerce, Integrations, and Notifications, each with small focused Lambdas. Do not create one repository per Lambda or a central platform-owner UI. Draft source, repositories, public runtime, logs, events, and deployment plans must not contain provider credentials, payment/identity/bank data, fiscal PII, or raw provider payloads. Validated `server/` descriptors may contain only non-secret policy and opaque references in draft source and private authoring packages; they must never be projected into browser, SSR, or public runtime artifacts. Public artifacts use an exact allowlist and are inspected before credentials or upload; validation has no OIDC, and only the exact validated commit may deploy. Remote authoring requires an explicit environment, and pulls validate domain, environment, and stage before writing. Config Authoring may deploy only from a verified allowlisted artifact behind IAM. Accountant/legal answers, validated Stripe/provider setup, HostGator authorization or an approved provider, and any open live-security incident remain gates for real Commerce/Notifications activation; do not infer tax defaults, enable Stripe Tax or SMTP, capture live fiscal PII, or provision provider secrets before [the approved plan](./plan/infrastructure-server-only-integrations-1.md) closes those gates.

Draft deployment must prove the exact merged same-repository PR for `dev -> test` or `test -> main`, its merge and parent SHAs, the push event's first parent, and current target tip; ancestry alone fails. Serialize by repository/environment. GitHub Environments and AWS OIDC trust independently require the exact deployment branch. Provision roles only from `docs/drafts-registry.json`; bootstrap fails when native branch or Environment protection is missing.

While protected draft branches require zero approvals, every identity with write and merge permission is a trusted deployment authority because repository code contains the workflow and verifier. If that trust set expands beyond fully trusted operators, require an independent reviewer or move privileged verification to an immutable reusable workflow outside the draft repository. Setup must pin the required `guard` check to the verified GitHub Actions app, allow no PR bypass identities, read branch and Environment protection back after writing it, anchor the GitHub owner to the registry, and reject ambiguous or invalid IAM role names before any AWS mutation.

All repository changes must be promoted by protected pull requests in order: `dev -> test -> main`. Before each promotion, synchronize the target branch history back into the source branch through a validated PR when needed so the promotion is conflict-free and no branch history is discarded.

Do not make the Codex Security UI a release dependency. If it is unavailable or renders blank, continue with deterministic repository tests, diff and secret scanning, live policy readback, and an independent security-focused review; record any tool failure instead of treating an empty view as a clean result.
